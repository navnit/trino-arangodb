# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Trino connector plugin (`packaging: trino-plugin`) that lets Trino run SQL queries against ArangoDB. ArangoDB databases map to Trino schemas, collections map to tables. Currently at milestone M6-C ("schema sources"): read-only, with equality/range filter and limit pushdown (M1/M2), plus per-shard parallel splits on cluster deployments for eligible (non-smart, multi-shard hash) collections (M3); recursive ARRAY/ROW/DECIMAL value materialization (M4); COUNT/SUM/MIN/MAX/AVG + GROUP BY pushed into a single-split AQL `COLLECT` (M5); row-count table statistics from the cheap collection count, TTL-cached (M6-A); an AQL passthrough table function, `arango.system.query` (M6-B); and a user-curated schema-override collection (`trino_schema` by default) that, per table, takes full precedence over sampling and unlocks declared `decimal(p,s)`/`timestamp(3)`/`timestamp(3) with time zone` columns not reachable through inference alone (M6-C).

## Commands

Maven is not on `PATH` by default in this environment; if `mvn` reports "command not found", run:

```bash
source ~/.sdkman/bin/sdkman-init.sh
```

Build requires Java 25 (`maven.compiler.release=25` in `pom.xml`) — the project tracks Trino 483 (`dep.trino.version`), whose artifacts (`trino-spi`, `io.airlift:*` at 439) ship Java-25 bytecode. The Trino-483/JDK-25-mandatory flags — `--add-modules=jdk.incubator.vector` (trino-spi's `BlockEncodingSimdSupport` statically initializes `jdk.incubator.vector.VectorShape`) and `--sun-misc-unsafe-memory-access=allow` — live in a shared `trino.test.argLine` pom property consumed by both the surefire `argLine` and the failsafe `argLine`: failsafe is a separate plugin that does not inherit surefire's `<argLine>`, and needs the same flags because `PassthroughClusterIT` boots a `DistributedQueryRunner` under failsafe (the first failsafe IT to do so).

```bash
mvn package                          # build the trino-plugin artifact
mvn test                             # run the full test suite
mvn test -Dtest=TypeMapperTest       # run a single test class
mvn test -Dtest=TypeMapperTest#mergeIntAndFloatWidensToDouble   # single test method
```

Most test classes (`ArangoClientTest`, `ArangoConnectorQueryTest`, `ArangoPageSourceProviderTest`, and others using `TestingArangoServer`) spin up a real ArangoDB container via Testcontainers — **Docker must be running locally** for `mvn test` to pass. No mocking framework is used anywhere in the test suite; where a test does need to avoid hitting a live server (e.g. `ArangoMetadataTest`'s error-path cases), it uses hand-written `ArangoClient` subclasses as test doubles rather than a container. End-to-end SQL queries run against a live container via Trino's `DistributedQueryRunner` (see `ArangoConnectorQueryTest`).

### Static analysis

The build wires a Docker-free static-analysis stack. The three gates are **not** bound to the `verify` lifecycle — they run as explicit goals from a dedicated fast CI job (and locally / via pre-commit). Binding them to `verify` would make the Docker test jobs' `mvn verify` also run Spotless, whose `ratchetFrom=origin/master` needs a ref those jobs don't fetch:

```bash
mvn spotless:check      # google-java-format (AOSP/4-space), ratcheted to origin/master
mvn spotless:apply      # auto-fix formatting on changed files
mvn checkstyle:check    # semantic conventions (imports, naming, @Override, equals/hashCode, empty blocks)
mvn compile spotbugs:check   # bytecode bug patterns + FindSecBugs (needs compiled classes)
```

Key design points (full rationale in `docs/superpowers/specs/2026-07-22-static-analysis-tooling-design.md`):

- **Spotless is ratcheted** (`ratchetFrom=origin/master`): it enforces formatting only on files changed vs `master`, so the hand-tuned M1–M3 source is untouched. It uses google-java-format's **AOSP style (4-space)** to match the existing indentation — default GJF is 2-space and would reindent every touched file.
- **Checkstyle and SpotBugs findings on the pre-existing M1–M3 code are grandfathered**, mirroring the ratchet: existing files are suppressed (`config/checkstyle/suppressions.xml`, `config/spotbugs/spotbugs-exclude.xml`, each entry with a documented reason), and the gates enforce on new/changed code going forward. Fixing them in place is not viable because the ratchet is file-granular, so any edit would trigger a full-file GJF reflow.
- Tool version floors (google-java-format 1.35, SpotBugs 4.10, Spotless 3.x) exist for **JDK 25 support**: older versions call javac internals / bundle an ASM that break on a JDK-25 toolchain. CI now pins JDK 25 (matching `maven.compiler.release`); these floors are what let the whole toolchain run there.
- Optional local git hooks live in `.pre-commit-config.yaml` (`pre-commit install`); Dependabot config in `.github/dependabot.yml`.

### pom.xml is a standalone module with no parent POM

This means several dependency versions that a real Trino connector would normally inherit from `io.trino:trino-root`'s `dependencyManagement` are pinned explicitly here instead, each with a long comment explaining *why* (`trino-spi`-transitive `provided`-scope pins for `jackson-annotations`/`opentelemetry-api`/`opentelemetry-context`; `io.airlift` `jaxrs`/`http-client`/`jmx` pinned to `336` to fix a `discovery-server:1.37`-induced skew; `junit-jupiter-api`/`junit-platform-launcher` pins to fix JUnit5 mediation). **Do not remove or "simplify" these pins** without reading the comment above each one — they exist to work around real dependency-mediation bugs, not stylistic preference. The Surefire `argLine` and `api.version=1.51` system property are similarly required workarounds (the latter for Testcontainers 1.20.4's shaded docker-java client rejecting modern Docker Engine's default API version) — also documented inline.

## Architecture

### SPI wiring (Plugin → Connector)

Trino discovers the connector via `ArangoPlugin.getConnectorFactories()` → `ArangoConnectorFactory` (registered under the name `"arangodb"`). `ArangoConnectorFactory.create()` boots an Airlift `Bootstrap`/Guice `Injector` from `ArangoModule`, then pulls a singleton `ArangoConnector` out of it. `ArangoModule` binds `ArangoClient`, `TypeMapper`, `SchemaResolver`, `AqlBuilder`, `ArangoMetadata`, `ArangoSplitManager`, `ArangoPageSourceProvider`, and `ArangoConnector` as `Scopes.SINGLETON`; `ArangoConfig` is bound separately via Airlift's `configBinder(...).bindConfig(...)`. `ArangoConnector` just hands out these singletons for `getMetadata()`/`getSplitManager()`/`getPageSourceProvider()`/`getTableFunctions()` (the last returns the injected `Set<ConnectorTableFunction>`, empty unless `arangodb.query-function-enabled` is `true`), and its `shutdown()` calls `LifeCycleManager.stop()`, which triggers `ArangoClient`'s `@PreDestroy` (`close()` on the underlying `ArangoDB` driver instance).

`ArangoConfig` (bound via Airlift's `@Config`) holds every user-facing setting: `arangodb.hosts` (comma-separated `host:port` list), `arangodb.user`, `arangodb.password` (`@ConfigSecuritySensitive`), `arangodb.schema.sample-size` (default 1000), `arangodb.schema.sample-random`, `arangodb.schema.mixed-type-strategy` (`VARCHAR` or `JSON`, though `JSON` is not actually wired up yet — see `TypeMapper.merge`), `arangodb.schema.cache-ttl` (default `5m` — how long a resolved schema is cached before re-sampling), `arangodb.type-coercion` (`lenient`, the default, or `strict` — see `ArangoPageSource.appendValue` and `ArangoMetadata.applyFilter` below), `arangodb.shards-per-split` (default `1` — target number of shards grouped into each split on cluster fan-out), `arangodb.max-splits` (default `32` — hard cap on the number of splits per collection scan; this cap can force more shards into a single group than `arangodb.shards-per-split` once `ceil(shardCount / shardsPerSplit)` exceeds it), `arangodb.aggregation-pushdown-enabled` (default `true` — set to `false` to compute every aggregate in Trino rather than pushing a `COLLECT` into AQL; see `AggregatePushdown` below), `arangodb.shard-parallelism-enabled` (default `true` — set to `false` to force single-split scans unconditionally and never invoke the internal `shardIds` option; see `ArangoSplitManager` below), `arangodb.query-function-enabled` (default `true` — registers `arango.system.query`; `false` removes the function entirely, so callers see Trino's "not registered" rather than a tailored error), `arangodb.statistics-enabled` (default `true` — expose row-count table statistics; `false` returns unknown statistics everywhere), `arangodb.statistics.cache-ttl` (default `5m` — how long a collection row count is cached for planning), and `arangodb.schema-collection` (default `trino_schema` — the per-database collection `SchemaOverrideReader` reads for user-curated schema-override documents; there is no kill switch, since an absent collection *is* the disabled state — see `SchemaResolver` below).

### Read path (Metadata → SplitManager → PageSourceProvider → PageSource)

This is the part that spans the most files and is worth understanding as one flow:

1. **`ArangoMetadata`** (`ConnectorMetadata`) — `listSchemaNames` = ArangoDB databases, `listTables`/`getTableHandle` = non-system collections within a database. Column info comes from `resolve()`, which calls `SchemaResolver.resolveColumns()` and caches the result per `SchemaTableName` in a Guava `Cache` with `expireAfterWrite(arangodb.schema.cache-ttl)` (default 5m).
2. **`SchemaResolver`** (M6-C) first consults `SchemaOverrideReader.read(database, table)`; a present result *is* the complete user-column set for that table — sampling never runs for it. The reader follows a fixed **probe → fetch → strict validation → replace** sequence: **probe** a per-database Guava cache (`expireAfterWrite(arangodb.schema.cache-ttl)`) for whether `arangodb.schema-collection` exists at all — the common no-override deployment must cost one cheap existence check per database per TTL, not a failed AQL per table; absent → fall through to sampling at `DEBUG`, no AQL issued. If present, **fetch** via a single bind-parameterized `FOR d IN @@sc FILTER d.table == @t LIMIT 2 RETURN d` (`ArangoClient.fetchSchemaOverrideDocs`) — `LIMIT 2` exists purely to make "two docs claim this table" detectable without a full scan. Zero docs → fall through to sampling. Two-or-more → `ARANGODB_SCHEMA_ERROR`, ambiguity is never resolved silently. Exactly one doc → **strict validation** (`SchemaOverrideReader.parse` + `DeclaredTypes.parse`/`validate`): every unrecognized key anywhere in the doc or a field object is rejected (this is what catches a `"hiden"` typo and rejects `path` as "not yet supported" rather than silently ignoring it — `path`-based renaming is deferred, so a declared `name` is simultaneously the Trino column name *and* the exact, case-sensitive stored attribute name); `name` must be non-empty, not `_`-prefixed, and not a case-insensitive duplicate of another field (Trino resolves column identifiers case-insensitively, so `Total`/`total` would collide at query time); `type` is parsed via the injected `TypeManager.fromSqlType` (bound from `ConnectorContext` at factory time — never a hand-rolled second parser) then checked against `DeclaredTypes`'s recursive allowlist (described below); a declared name matching no stored attribute is *not* validated against live data — the override's entire point is to avoid sampling — so it silently reads all-`NULL` rather than erroring, in both coercion modes (`ValueMaterializer` nulls an absent map key before any mismatch check ever runs). A validation failure anywhere raises `ARANGODB_SCHEMA_ERROR` (new in M6-C, code `2`, `USER_ERROR`) naming the table and the offending field/key; this is raised lazily, at column-resolution time for that one table — `SHOW TABLES` and column enumeration for sibling tables are unaffected. Errors reading the override collection itself route by ArangoDB error number: `1203` (collection not found — a race between the probe and fetch) degrades to "no override, fall through to sampling," mirroring `isDatabaseNotFound`'s 1228 split; a forbidden-access response (error number `11` or HTTP `403`, pinned by `AqlSchemaOverrideAssumptionsTest` as `ArangoClient.ERROR_NUM_FORBIDDEN`/`HTTP_FORBIDDEN`) fails loud with a diagnostic naming `arangodb.schema-collection` and suggesting "grant read on it, or drop it" — a stable misconfiguration should be fixed, not silently degraded around; anything else also fails loud as `GENERIC_INTERNAL_ERROR`, unlike M6-A statistics — schema is load-bearing, not advisory. Once **replace**d, `SchemaResolver` appends the same system columns (`_key`/`_id`/`_rev` hidden, `_from`/`_to` for edge collections) via the shared `appendSystemColumns` helper so the override and sampling paths can never drift on that part.

   Absent an override (or with no override collection at all), `SchemaResolver` falls back to sampling up to `sampleSize` documents from the collection (`ArangoClient.sampleDocuments`) and infers a schema by taking the *union* of fields across all sampled docs, merging types per field via `TypeMapper.merge`. System attributes (`_key`, `_id`, `_rev`) are always added as hidden `VARCHAR` columns; `_from`/`_to` are added as visible `VARCHAR` columns only when the collection is an edge collection. A field seen only as `null` across the whole sample resolves through the `UnknownType.UNKNOWN` bottom sentinel down to `VARCHAR` (recursively, even nested inside `ROW`/`ARRAY`) — see `SchemaResolver.resolveUnknown`.

   **`DeclaredTypes`'s recursive allowlist** admits exactly what `ValueMaterializer` can materialize exactly: `boolean`/`bigint`/`double`/unbounded `varchar` (checked via `VarcharType::isUnbounded`, not `instanceof`, so `varchar(n)` doesn't slip through the unchecked-slice write path); `decimal(p,s)` (any precision/scale); `timestamp(3)` and `timestamp(3) with time zone` (precision 3 only); and `array(e)`/`row("f" t, ...)` recursively, with `row` additionally requiring every field to be named and free of case-insensitive duplicates (`fromSqlType` happily parses `row(varchar)` — anonymous — and `row(a varchar, a bigint)` — duplicate — both of which would otherwise crash or silently collide at materialization time). Admission is by resolved `Type` object, not raw spelling, so alias forms that resolve to an admitted type pass for free: bare `timestamp` (→ `timestamp(3)`), bare `decimal` (→ `decimal(38,0)`), `timestamp(3) without time zone` (→ `timestamp(3)`). Rejected: bounded `varchar(n)`, `char`, `date`, `time`, `real`/`integer`/`smallint`/`tinyint`, `json`, `uuid`, `varbinary`, and any other timestamp precision. `fromSqlType` failures (syntactically invalid like `decimal(`, or a syntactically-valid-but-unknown type name) both arrive as the *engine's* Guava `UncheckedExecutionException` wrapping a plugin-invisible `trino-parser` class, so `DeclaredTypes.parse` catches bare `RuntimeException` rather than naming either wrapped type — the only way to catch either from plugin code.

   **Case-sensitivity trap in declared `row(...)` fields**, documented rather than detected (detecting it would mean re-parsing the raw type string alongside `TypeManager`, i.e. building the second parser the whole `TypeManager`-adoption decision exists to avoid): an unquoted field name inside a type string is lowercased by the SQL parser, so `row(placedAt timestamp(3))` parses to field `placedat`, which then never matches a stored `placedAt` attribute — an all-`NULL` column with no error. `row("placedAt" timestamp(3))` (double-quoted) preserves case.
3. **`TypeMapper.inferType`/`merge`** implement the type-inference rules: `Boolean→BOOLEAN`, `Integer/Long→BIGINT`, `BigInteger` beyond 63 bits or `uint64→DECIMAL(38,0)`, other `Number→DOUBLE`, `String→VARCHAR`, `List→ARRAY(...)` (recursively merging element types), `Map→ROW(...)`. Merging an int-typed and double-typed occurrence of the same field widens to `DOUBLE`; merging any other genuinely incompatible pair falls back to `VARCHAR` regardless of `mixed-type-strategy` (the `JSON` strategy value exists in config but isn't implemented as an actual output type yet).
4. **`ArangoSplitManager`** decides, per table on every `getSplits` call, whether to fan a collection scan out into multiple `ArangoSplit`s (one per shard group) or fall back to a single split that scans the whole collection. When `arangodb.shard-parallelism-enabled` is `false` it always returns a single split. Otherwise it runs a pipeline implemented in the new `io.arango.trino.split` package: **discover** the collection's `ShardingInfo` (shard count, sharding strategy, SmartJoin attribute) → **allowlist gate** (`ShardEligibility`) — only non-smart hash-sharded collections (`hash`/`community-compat`/`enterprise-compat`) with more than one shard and no `smartJoinAttribute` are eligible; SmartGraph/SmartJoin collections are always excluded because their edges can live in multiple internal sub-shards, which would double-count rows under naive per-shard scanning → **enumerate** the collection's shard IDs → **group** them (`ShardGrouping.partition`) into `min(ceil(shardCount / arangodb.shards-per-split), arangodb.max-splits)` balanced groups, with every shard landing in exactly one group → **probe** (`ShardFanoutCapability`) whether the server can be trusted to honor the internal `shardIds` query option — a version pin (server must report ≥ 3.11) plus an active count-sum probe (Σ of per-group `shardIds`-scoped counts must equal the full collection count) for the actual groups about to be emitted, computed once per connector process and cached (an inconclusive probe, e.g. an empty collection, is retried rather than cached) → **emit** one `ArangoSplit` per shard group. A failure anywhere in this pipeline (ineligible collection, unconfirmed capability, or a discovery exception) falls back to a single split scanning the whole collection; a multi-shard collection that falls back this way logs a `WARN` so the fallback is observable, while a genuinely non-sharded/single-shard collection falls back silently at `DEBUG`.
5. **`ArangoMetadata.applyFilter`** pushes a `Constraint` down into the `ArangoTableHandle`'s stored `TupleDomain`, per-column, via `isPushable`: equality/IN (`ValueSet.isDiscreteSet()`) is pushable for `BOOLEAN`/`VARCHAR`/`BIGINT`/`DOUBLE`; numeric range is pushable only for `BIGINT`/`DOUBLE`. `AqlBuilder` renders each pushed comparison so the AQL predicate can't be satisfied by a value the read path would reject or read differently: `BOOLEAN`/`VARCHAR`/`BIGINT` compare bare (AQL `==`/`IN`/`<`/`>` are type-strict and the `BIGINT` read path is exact — `longValue()`, no rounding); `BIGINT` range guards only with a bare `IS_NUMBER(...)` (no integrality conjunct — AQL `FLOOR()` returns a `double`, so `d.f == FLOOR(d.f)` would false-miss a stored `int64` beyond 2⁵³ that reads back exactly, review finding C3; the guard doesn't need to exclude fractionals because `BIGINT` range is *prefilter-only* — see below — and the residual re-check drops them); and every `DOUBLE` comparison (eq/IN **and** range) is rendered as `IS_NUMBER(d.f) AND (d.f + 0.0) <op> @v` — the `+ 0.0` promotes a stored `int64` into double space so AQL compares exactly what `appendValue` reads via `doubleValue()` (ArangoDB otherwise compares `int64`-vs-`double` by exact mathematical value, which diverges from the rounded read path beyond 2⁵³ — review finding C1), and the `IS_NUMBER` guard precedes the arithmetic because `+ 0.0` coerces non-numbers. The promotion is `DOUBLE`-only: promoting `BIGINT` would round its exact read path and reintroduce the same class of bug in reverse. **Known limitation:** the `+ 0.0` arithmetic also nullifies a stored *non-finite* `double` (`Infinity`/`NaN`), so a fully-pushed `DOUBLE` predicate omits such a row server-side even though the read path would keep it. This is unreachable through normal JSON ingestion — ArangoDB cannot represent `Infinity`/`NaN` in JSON (it renders them as `(non-representable type double)`) — and can only occur for documents written by a native-VelocyPack driver; it is an accepted limitation (surfaced by the C3 re-review), not closed in M2. `IS NULL` (a null-allowing domain, caught by `isPushable`'s `domain.isNullAllowed()` check) always stays residual — AQL's null test operates on the raw stored value, which can diverge from Trino's post-coercion null-ness on a type mismatch. `IS NOT NULL` also always stays residual, but via the separate `values.isAll()` check just after it (its domain excludes null, so it never trips `isNullAllowed()`); `VARCHAR` range stays residual too, falling through to `isPushable`'s final type check since only `BIGINT`/`DOUBLE` range is pushable. Because the bare `IS_NUMBER` guard admits fractional values and integral values outside signed-64-bit range (both of which `appendValue` reads as `NULL`), a `BIGINT` range push is *prefilter-only*: it's applied in AQL **and** kept in Trino's residual for a post-read re-check (the constraint is not fully pushed down), whereas equality/IN and `DOUBLE` range are fully enforced by the pushed AQL alone (fully pushed down, nothing left residual). When `arangodb.type-coercion=strict`, `isPushable` always returns `false` — pushing a filter would let ArangoDB silently exclude a type-mismatched row server-side, which would suppress the `ARANGODB_TYPE_CONVERSION_ERROR` strict mode is supposed to raise, so strict mode declines all pushdown and evaluates every constraint as residual instead. `ArangoMetadata.applyLimit` similarly pushes a `LIMIT` into the handle, but `limitGuaranteed` now tracks `!config.isShardParallelismEnabled()`: with shard-parallelism enabled (the default), `ArangoSplitManager` may fan a collection out into multiple splits, each executing its own `LIMIT n` independently, so a pushed limit is a per-split reduction rather than a global guarantee and Trino must still enforce the final `LIMIT` itself over the merged results; only with `arangodb.shard-parallelism-enabled=false` (always single-split) is the pushed limit exact.
6. **`ArangoPageSourceProvider.createPageSource`** builds the AQL query via `AqlBuilder.buildScan`, which starts from a base `FOR d IN @@col` scan and appends a `FILTER` clause when the handle has a pushed `TupleDomain` (predicate values are bind-parameterized through `bindVars`) and a `LIMIT` clause when the handle has a pushed limit (the limit is appended as a literal integer directly into the AQL string, *not* bind-parameterized). The query always ends in a `RETURN {"col": d["col"], ...}` clause built by `buildReturnClause`, projecting exactly the requested columns as an object literal — there is no bare `RETURN d` form, even for an unfiltered/unlimited full scan. It constructs an `ArangoPageSource` over the resulting cursor. Structured columns (`ARRAY`/`ROW`/`DECIMAL`) materialize like any other since M4 — there is no up-front rejection anymore.
7. **`ArangoPageSource`** streams `ArangoCursor<Map>` into Trino `Page`s in batches of 1024 rows. Value coercion (`appendValue`) is *type-exact*: a stored value whose runtime type doesn't match the column's inferred Trino type is a mismatch, not something to coerce — no more `String.valueOf` or `longValue()` truncation. Under `arangodb.type-coercion=lenient` (the default) a mismatch reads as `NULL`; under `strict` it raises `TrinoException(ARANGODB_TYPE_CONVERSION_ERROR, ...)`. This is a deliberate M1 read-behavior change: a number stored under a `VARCHAR` column, or a fractional value (`42.5`) stored under a `BIGINT` column, now reads as `NULL` instead of being coerced. A `BIGINT` column does still accept a fractional-*free* `Double`/`Float`/`BigInteger` (e.g. stored `42.0` reads as `42`) — only genuine fractions are a mismatch; truncating them would silently disagree with a pushed range filter that already excluded them, which is the exact class of bug type-exactness closes. This exactness is also what lets `applyFilter` push equality/range predicates safely at all: the pushed AQL comparison and this read path are guaranteed to admit exactly the same values. Coercion of structured values lives in `io.arango.trino.type.ValueMaterializer` (`TypeMapper`'s read-side dual; `ArangoPageSource` itself stays pure cursor/paging and delegates to it) — materialization is recursive and leaf-level exact: a nested mismatch nulls only the offending element/field under `lenient` and raises `ARANGODB_TYPE_CONVERSION_ERROR` with a path to the offending leaf (e.g. `col[2].b`) under `strict`; an absent `ROW` field or a stored `null` at any depth is `NULL` in both modes, never treated as a mismatch; `DECIMAL(38,0)` accepts any integral number gated by `Decimals.overflows(..., 38)` — deliberately *not* the ±2⁶³ `BIGINT` bound, since uint64-range values like `1e19` must still read back correctly.

   **M6-C's declared-type leaves** dispatch on `Type` exactly like every other leaf, so a sampled `DECIMAL(38,0)` and a declared `decimal(38,0)` materialize through the identical code path — one exactness rule, not two. `DecimalType` now writes both short and long representations: `unscaledExact(value, scale)` converts a matching JSON number or decimal string to the column's exact scale with **no rounding** (an inexact fit at scale `s` is a mismatch, not a rounded write), then `p ≤ 18` (`ShortDecimalType`, which lacks `writeObject`) writes `unscaled.longValueExact()` via `writeLong`, while `p > 18` writes `Int128.valueOf(unscaled)` via `writeObject` — the pre-M6-C code wrote `Int128` unconditionally, which was only correct because inference only ever emitted `DECIMAL(38,0)`. A JSON number converts via `new BigDecimal(double)` — the double's **exact binary value**, deliberately never `BigDecimal.valueOf` (whose shortest-round-trip representation would silently diverge from "read exactly what's stored"): the consequence, stated plainly, is that a stored `double` matches a declared scale only on exact binary fit (`0.25` at `s=2` matches; `12.34` does not, since `new BigDecimal(12.34)` is `12.3399…`) — decimal **strings** are therefore the encoding the type actually exists for, and are the deliberate flip from every other leaf in this class: everywhere else a `String` under a numeric-typed column is an ordinary mismatch, but under `DecimalType` a string is a *first-class matching encoding*, converted via `new BigDecimal(String)`. `timestamp(3)` accepts an ISO-8601 **local** string (`LocalDateTime.parse`, `ISO_LOCAL_DATE_TIME`) and writes **epoch microseconds** (not millis — Trino's short `timestamp(3)` encoding is micros; the write uses `Math.multiplyExact`/`addExact` since `LocalDateTime.parse` accepts extended years whose epoch-micros value can overflow a `long`). `timestamp(3) with time zone` accepts an ISO-8601 string **with** an offset (`OffsetDateTime.parse`, `ISO_OFFSET_DATE_TIME`) and writes `DateTimeEncoding.packDateTimeWithZone`. Both timestamp leaves share a **bounds-checked-before-write, never-an-escaping-exception** rule matching the decimal leaf's overflow gate: fractional seconds finer than millis, a local string where an offset was declared (or vice versa), a sub-minute offset (`ISO_OFFSET_DATE_TIME` accepts `+05:30:15`; `TimeZoneKey.getTimeZoneKeyForOffset` throws on it), an offset beyond ±14:00 (the parser accepts up to ±18:00; Trino does not), or a 52-bit packed-millis/epoch-micros overflow — every one of these is caught pre-write and downgraded to an ordinary per-cell mismatch (lenient `NULL` / strict `ARANGODB_TYPE_CONVERSION_ERROR`), never a raw `ArithmeticException` or `TrinoException` escaping from inside a page-building lambda.

8. **`ArangoMetadata.applyAggregation`** (M5) pushes `COUNT`/`SUM`/`MIN`/`MAX`/`AVG` and single-grouping-set `GROUP BY` (including `SELECT DISTINCT`) into an AQL `COLLECT ... AGGREGATE`, rendered by `AqlBuilder.buildAggregate` as `FOR → FILTER → COLLECT/AGGREGATE → LIMIT → RETURN`. The decision lives in the pure `AggregatePushdown.plan` gate; the result is an `ArangoAggregation` descriptor stored on the handle, whose *presence is* the "aggregated" flag. `ArangoSplitManager` short-circuits an aggregated handle to **exactly one split before any shard discovery** — Trino treats connector aggregate output as final, so N splits would emit N duplicate final rows (spec §6.4) — which is also why `applyLimit` reports `limitGuaranteed` for such a handle. Aggregate outputs are ordinary `ArangoColumnHandle`s carrying `AggregateFunction.getOutputType()`, so **`ArangoPageSource` and `ValueMaterializer` are untouched by M5**.

   The exactness rule is the same one M2 established for filters, but stricter: `applyFilter` may push a *prefilter* and let Trino re-check the residual, whereas **aggregation has no residual** — Trino replaces the aggregation node outright, so a wrong aggregate is simply a wrong answer. Everything claimed must therefore be exact. `ColumnGuard` renders `ValueMaterializer`'s coercion as an AQL guard so the pushed query computes over precisely the values the read path would emit; values the reader nulls become AQL `null`, which AQL's aggregates ignore. What this rules out: `min`/`max` on `VARCHAR` (ArangoDB orders strings by server collation, Trino by codepoint) and `sum`/`avg` on `BIGINT` (AQL accumulates in double — `SUM([2^53+1, 1])` is `2^53`, and Trino's loud `sum(bigint)` overflow would become silent). Three renderings exist purely to reconcile AQL with SQL null semantics, each pinned in `AqlSemanticsAssumptionsTest`: `count(col)` is `SUM(guard ? 1 : 0)` wrapped `== null ? 0` (AQL `COUNT` is an alias of `LENGTH` and counts nulls; AQL `SUM` over zero rows is `null`), `sum` carries a companion count so an all-null group yields `NULL` rather than AQL's `0`, and a `BIGINT` grouping key is normalized `(a == 0 ? 0 : a)` because `COLLECT` under the `hash` method — the one the optimizer picks here — puts a stored `-0.0` in its own group even though it reads back as `0`, which would emit one Trino group as two final rows. Two non-obvious declines: `strict` coercion disables aggregation pushdown entirely (mirroring `isPushable`), and a **prefilter-only constraint (`BIGINT` range) declines it too** — that constraint is enforced jointly by AQL and Trino's residual re-check, so aggregating server-side alone would count rows the re-check drops. That last rule is load-bearing, not defensive: Trino fuses filters into a `ScanFilterProject` and *will* push an aggregate through one (proven by the fully-pushed `DOUBLE`-range case in `ArangoConnectorAggregationTest`).

9. **`ArangoMetadata.getTableStatistics`** (M6-A) returns a row-count-only `TableStatistics` from `ArangoClient.countDocuments` (the metadata-level `GET /_api/collection/{name}/count`, deliberately not the AQL-based `countWithShardIds`), cached per `SchemaTableName` in a second Guava cache with `expireAfterWrite(arangodb.statistics.cache-ttl)`. It is a guard chain: `arangodb.statistics-enabled=false` → empty; `ArangoQueryHandle` → empty (opaque AQL); aggregated handle → `Estimate.of(1)` for a global aggregate (empty `groupingColumns` = exactly one output row), `Estimate.of(limit)` for a grouped one carrying a pushed limit (an aggregated handle is always a single split with `LIMIT` after the `COLLECT`, so the cap is exact), empty for a grouped one without; otherwise the cached count, with `min(count, limit)` applied only when `arangodb.shard-parallelism-enabled=false` (mirroring `applyLimit`'s `limitGuaranteed` — under fan-out the engine's retained `LimitNode` applies the min itself). A pushed filter does **not** change the number (recorded decision — base-JDBC precedent; a fully-pushed filter's scan estimate is therefore an upper bound). Count failures degrade to `TableStatistics.empty()` + `WARN` instead of the class's usual `GENERIC_INTERNAL_ERROR` rethrow — statistics are advisory, and failing planning over an optional signal would kill queries whose scan path still works; failures are never negative-cached. The four pushdown hooks keep passing `precalculateStatistics=false` — flipping it would have the engine re-derive post-pushdown stats via `FilterStatsRule`, which with no column statistics yields *unknown* and would silently discard the row count.

### Passthrough path (M6-B)

**`ArangoQueryFunction`** registers `arango.system.query(database, query)`, a raw AQL passthrough table function. `QueryFunction.analyze()` has one correctness invariant, checked in a fixed order: `explainPlan` (a raw `POST /_api/explain`, since the driver's typed API doesn't expose `plan.collections[].type`) → `AqlReadOnlyGate.check`, an **allowlist** over every entry in `plan.collections[]` — admitted only if every collection's access `type` is exactly `"read"` — that **fails closed** on anything unrecognized (missing `plan`/`collections`, or a non-`read` type) and additionally rejects any `_`-prefixed collection name — system collections stay hidden from passthrough the same way they're hidden from `listTables` (a collection entry whose name isn't a string falls back to a placeholder and still runs the exact `"read"` check, so it can't open the gate; it just means the `_`-prefix hardening, which needs a real name, doesn't cover it) → only then `firstBatch`, which actually executes the query (`stream(true)`, cursor always disposed in a `finally`, so the planning-time execution never leaves a server-side snapshot open). Gate before execute is load-bearing: reordering would run a query the gate was about to reject. Schema derivation reuses `TypeMapper.merge`/`SchemaResolver.resolveUnknown` field-by-field over the batch — deliberately the *same* inference `SchemaResolver` uses, so a passed-through document infers identically to a scanned one — and rejects (`INVALID_FUNCTION_ARGUMENT`) a non-object row, an empty result (no rows to infer a schema from), an all-empty-object result (no columns), or any object with an empty-string attribute key. The result travels on a separate `ArangoQueryHandle` (not a field on `ArangoTableHandle`), so "filter/limit/projection/aggregation pushed at opaque user AQL" is unrepresentable rather than a state every hook must remember to decline: `applyFilter`, `applyAggregation`, `applyLimit`, and `applyProjection` each `instanceof`-check for `ArangoQueryHandle` first and decline (`Optional.empty()`) before ever casting to `ArangoTableHandle`, and `ArangoSplitManager.getSplits` short-circuits it to exactly one split before any shard discovery, for the same duplicate-final-row reason M5's aggregation short-circuit exists. Execution runs the user's AQL **verbatim** (`ArangoClient.queryPassthrough`) through `PassthroughCursor`, an `Object`-typed-to-`Map`-typed adapter that lets `ArangoPageSource` stay untouched; a non-object row surfaces there as the same `INVALID_FUNCTION_ARGUMENT` guidance `analyze()` gives, rather than a raw driver deserialization failure. Errors route by ArangoDB error number: 1228 (database not found) → `SchemaNotFoundException` (not `TableNotFoundException` — the missing thing is a database); 1203 (collection/view not found) and the 1500–1599 AQL-error range → `INVALID_FUNCTION_ARGUMENT` carrying the server message (both are user errors in the supplied query string); a write-plan rejection from the gate → the connector's own `ARANGODB_QUERY_NOT_READ_ONLY`; anything else → `GENERIC_INTERNAL_ERROR`, matching `ArangoMetadata`'s translation rule.

### Error translation

`ArangoMetadata` distinguishes "the ArangoDB database doesn't exist" (driver error number 1228, checked via `isDatabaseNotFound`) from every other `ArangoDBException`. The former is treated as Trino's normal "schema/table not found" (return `null` / skip), while everything else (auth failure, network partition, etc.) is rethrown as `TrinoException(GENERIC_INTERNAL_ERROR, ...)` so real failures aren't silently swallowed as "not found."

### `information_schema.columns` bulk-listing gap (pre-existing, not M6-C)

`ArangoMetadata` implements no `streamRelationColumns`/`streamTableColumns`, so `SELECT * FROM information_schema.columns WHERE table_schema = '...'` with no `table_name` predicate falls back to Trino's engine-driven per-table resolution path and returns **zero rows** for every schema, healthy or not — a `table_name` equality predicate (or `SHOW COLUMNS FROM <table>`) resolves columns correctly. This was observed (not introduced) while e2e-testing M6-C's lazy per-table validation failure (a malformed override doc does *not* poison schema-wide enumeration — `SHOW TABLES`, `SHOW COLUMNS` on sibling tables, and predicate-scoped `information_schema.columns` queries all still work correctly for tables other than the malformed one), and is called out here as an unrelated, pre-existing connector gap: fixing it would mean implementing `streamRelationColumns`/`streamTableColumns`, out of scope for M6-C.

### `UnknownType` relocation

`io.arango.trino.type.UnknownType` is a verbatim Apache-2.0 relocation of Trino's own `io.trino.type.UnknownType`. It had to be copied rather than depended on: Trino's real `UnknownType` lives in the `trino-main` query-engine module, not in the public `trino-spi` contract a connector plugin can depend on, and Trino's plugin classloader only exposes `trino-spi` classes to plugins — a direct reference would fail with `NoClassDefFoundError` at runtime even if it compiled. This is documented in the class's own Javadoc and in `NOTICE`.

### Package layout

- `io.arango.trino` — SPI implementation classes (`ArangoPlugin`, `ArangoConnectorFactory`, `ArangoModule`, `ArangoConnector`, `ArangoConfig`, `ArangoMetadata`, `ArangoSplitManager`, `ArangoPageSourceProvider`, `ArangoPageSource`, `ArangoTransactionHandle`)
- `io.arango.trino.client` — `ArangoClient`, the sole wrapper around the ArangoDB Java driver (`ArangoDB`/`ArangoCursor`); also holds test-only seeding helpers (`createDatabaseForTest`, `insertForTest`, etc.) used by both unit and integration tests
- `io.arango.trino.handle` — SPI handle records (`ArangoTableHandle`, `ArangoColumnHandle`, `ArangoSplit`, `ArangoQueryHandle` — the separate `ConnectorTableHandle` for passthrough queries), all Jackson-serializable
- `io.arango.trino.schema` — `SchemaResolver`, the sampling/inference pipeline; `SchemaOverrideReader` (M6-C), the probe → fetch → strict-validate reader for the `arangodb.schema-collection` override collection, consulted before sampling runs; `DeclaredTypes` (M6-C), the recursive allowlist over `TypeManager.fromSqlType` output that admits exactly the types `ValueMaterializer` can materialize
- `io.arango.trino.type` — `TypeMapper`, `ValueMaterializer`, and the relocated `UnknownType`
- `io.arango.trino.aql` — `AqlBuilder`, translates a table scan into an AQL query string + bind vars
- `io.arango.trino.aggregation` — aggregation pushdown: `ColumnGuard` (renders `ValueMaterializer`'s coercion as an AQL guard expression — the one place M5's exactness invariant lives), `AggregateSpec`/`ArangoAggregation` (the pushed-aggregation descriptor carried on the table handle), `AggregatePushdown` (the pure decline gate implementing the exactness matrix)
- `io.arango.trino.split` — shard-parallel fan-out logic: `ShardingInfo` (record: shard count / sharding strategy / SmartJoin attribute), `ShardEligibility` (the non-smart-hash allowlist gate), `ShardGrouping` (partitions shard IDs into balanced split groups), `ShardFanoutCapability` (version pin + lazy-cached active count-sum probe gating use of the internal `shardIds` option)
- `io.arango.trino.ptf` (M6-B) — `arango.system.query` table function: `ArangoQueryFunction` (the `Provider<ConnectorTableFunction>` plus its nested `QueryFunction`/`QueryFunctionHandle`), `AqlReadOnlyGate` (the one place M6-B's safety invariant lives), `PassthroughCursor` (the `Object`→`Map` cursor adapter that keeps `ArangoPageSource` untouched)

`ArangoModule` is now an `AbstractConfigurationAwareModule` rather than a plain `com.google.inject.Module` implementation: registering `ArangoQueryFunction` conditionally on `arangodb.query-function-enabled` needs Airlift's `conditionalModule`, which requires that base class. The `Set<ConnectorTableFunction>` multibinder itself is always bound (even with the flag off) — `ArangoConnector` injects the set unconditionally, and "disabled" must mean an *empty* set, not a missing binding — while the actual `toProvider(ArangoQueryFunction.class)` binding is added only inside the conditional block.

`TestingArangoServer` (`src/test`) wraps the Testcontainers-managed ArangoDB instance shared by integration-style tests; `TestingArangoCluster` (`src/test`) similarly wraps a real multi-node ArangoDB cluster (coordinator/agency/dbservers, via Testcontainers' Compose support) used by the cluster ITs (`ShardParallelClusterIT`, `ShardParallelCorrectnessIT`, `PassthroughClusterIT`).
